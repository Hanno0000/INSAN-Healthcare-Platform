# 13 — Future Expansion — Module by Module (Replit Implementation)

> **Document Version:** 1.1
> **Status:** Final
> **Last Updated:** 2025-07-16
> **Source of Truth:** Yes

> **READ ONLY — Do not implement any of these during the initial build.** This document exists to validate that current architecture decisions support future growth.

> هذا الملف يكمّل قسم "Future Extensibility Hooks" المختصر في `../architecture/01_ARCHITECTURE.md` بشرح تفصيلي، خطوة بخطوة، لكل نوع توسّع محتمل — بحيث أي إضافة مستقبلية تتم **دون إعادة هيكلة الأساس**.

---

## 1. إضافة صفحة جديدة للموقع العام

**الحالة الشائعة (لا تحتاج كود إطلاقاً):**
1. من لوحة التحكم → Pages → "صفحة جديدة".
2. تُبنى بالكامل عبر Page Builder من المكونات المسجّلة أصلاً في `../ui/07_UI_COMPONENT_INVENTORY.md`.
3. تُضاف كعنصر في `NavigationItem` لو لازم تظهر بالقائمة.

**الحالة النادرة (تحتاج Layout مخصص فعلاً، مثال: صفحة تفاعلية جداً بمنطق خاص):**
1. تُضاف كمسار Next.js جديد تحت `app/[locale]/(public)/`.
2. لو احتاجت بيانات جديدة، تُضاف عبر نفس نمط `customFields` على `Page` أولاً، وتُرفَّع لحقول حقيقية فقط لو استقرّ الاستخدام.

---

## 2. إضافة موديول/كيان محتوى جديد بالكامل

**مثال تطبيقي:** لاحقاً قد يُطلب "برنامج كبارنا" (Senior Care Program) ككيان مستقل له صفحته الخاصة، وليس مجرد قسم داخل مركز طبي.

**خطوات الإضافة (نمط ثابت لأي كيان جديد):**
1. **Database:** موديول Prisma جديد بنفس القواعد المتبعة في `../database/03_DATABASE_SCHEMA.md` (حقول `Json {ar,en}`، `status ContentStatus`، `customFields Json`، علاقات M:N عبر جدول ربط صريح لو لزم).
2. **API:** موديول NestJS جديد يتبع **العقد الموحّد** بالضبط كما هو موضّح في `../api/04_API_SPECIFICATION.md` (List/Get/Create/Update/Publish/Delete) — لا حاجة لاختراع نمط جديد.
3. **الصلاحيات:** إضافة مفتاح جديد في كائن `permissions` بجدول `Role` (مثال: `"senior-care": ["view","create","edit","publish","delete"]`) — بدون تعديل منطق الـ `PermissionsGuard` نفسه.
4. **الصفحة العامة:** تُوثَّق بنفس قالب `../architecture/02_INFORMATION_ARCHITECTURE_AND_PAGES.md` (Purpose/URL/SEO/Sections...).
5. **شاشة الأدمن:** تُبنى بنفس قالب `../admin/06_ADMIN_DASHBOARD_SPECIFICATION.md` (جدول + نموذج + صلاحيات).

> **الفكرة الأساسية:** كل الكيانات في هذا المشروع مبنية بنمط متطابق تماماً (Hospital, MedicalCenter, Doctor, NewsPost...) عمداً — فإضافة كيان رقم 15 مطابقة تماماً لإضافة كيان رقم 5، بدون أي استثناء أو حالة خاصة.

## 3. الترقية لنظام حجز حقيقي (Real Booking System)

الوضع الحالي: `AppointmentRequest` = "طلب" يتابعه فريق العمليات يدوياً (تليفون/واتساب).

**الترقية المستقبلية:**
1. إضافة جدول `Slot` (معاد متاح لكل طبيب/عيادة: تاريخ، وقت، سعة).
2. إضافة `Booking` كامتداد لـ `AppointmentRequest` (نفس نقطة الدخول للزائر — نموذج الحجز الحالي لا يتغيّر من منظور المستخدم، فقط يصبح مربوطاً بـ Slot حقيقي بدل "تاريخ مفضّل" نصّي).
3. تكامل تقويم (Calendar) اختياري للأطباء لإدارة توفرهم من لوحة التحكم.
4. **لا حاجة لتعديل** `AppointmentForm` بالواجهة العامة إلا بإضافة خطوة اختيار Slot بدل حقل تاريخ حر.

## 4. نظام الإضافات (Plugins Architecture)

لو احتاج المشروع مستقبلاً دمج أدوات طرف ثالث (مثال: نظام حجز خارجي، أداة تسويقية) كـ "إضافات" وليست جزءاً أساسياً من الكود:

1. **جدول `Extension`** جديد: `{ key, name, isEnabled, config Json, permissionsNamespace }`.
2. كل Plugin يُبنى كـ **NestJS Dynamic Module** منفصل تماماً، يُحمَّل شرطياً فقط لو `isEnabled=true`، وله Namespace صلاحيات خاص به (مثال: `plugin:booking-sync`) بدل التداخل مع صلاحيات النظام الأساسي.
3. أي Plugin بالواجهة (شاشة أدمن إضافية) يُسجَّل في Sidebar Navigation **ديناميكياً** حسب الإضافات المفعّلة، وليس Hardcoded بقائمة القوائم الأساسية.
4. **مبدأ العزل:** أي خطأ أو تعطّل في Plugin **لا يجب أن يوقف** النظام الأساسي — يُغلَّف استدعاؤه دائماً بـ Try/Catch على مستوى الـ Module Loader.

## 5. لوحات تشغيلية داخلية جديدة (Internal Operational Dashboards)

مثال: "لوحة عمليات المستشفى" لفريق غير تسويقي (متابعة إشغال، مخزون، جدولة داخلية) — خارج نطاق موقع تسويقي عام.

**نمط الإضافة:**
1. تُضاف كتطبيق جديد `apps/ops-dashboard` داخل نفس الـ Monorepo (Turborepo)، تستهلك **نفس** الـ NestJS API (`apps/api`) — لا API منفصل ولا قاعدة بيانات منفصلة.
2. تُضاف أدوار/صلاحيات مخصصة لهذا التطبيق (Namespace منفصل، مثال: `ops:*`) بدون التأثير على أدوار Marketing/CMS الحالية.
3. تستفيد من نفس `packages/ui` (نظام التصميم المشترك) لضمان اتساق بصري، حتى لو الجمهور مختلف (موظفين داخليين وليس عامة الناس).

---

## 6. تطبيق موبايل مستقبلي (Mobile App)

الـ API مبني أصلاً API-first وموثّق بـ OpenAPI (`../api/04_API_SPECIFICATION.md`)، فتطبيق الموبايل (React Native / Flutter) يستهلك **نفس** الـ Endpoints تماماً بدون أي تعديل بالـ Backend، فيما عدا:
- **المصادقة:** بدل `httpOnly Cookie` (خاص بالمتصفح)، الموبايل يخزّن الـ `refreshToken` في Secure Storage خاص بالنظام (iOS Keychain / Android Keystore) — تعديل بسيط بطبقة الـ Client فقط، ونفس Endpoints `/auth/*` بلا تغيير.
- **Push Notifications:** نقطة تمديد جاهزة عبر نفس `jobs/` Worker الموجود أصلاً (يُضاف Handler جديد للإشعارات بدل/بجانب الإشعار الداخلي الحالي).

---

## 7. بوابة المرضى المستقبلية (Patient Portal)

**الفرق الجوهري عن نظام الأدمن الحالي:** المريض يرى بياناته الشخصية فقط (وليس نظام أدوار RBAC مؤسسي)، لذلك يُبنى كنظام صلاحيات **منفصل منطقياً**:
1. جدول `Patient` جديد (منفصل عن `User` الخاص بموظفي لوحة التحكم) — نفس آلية JWT لكن بـ Scope مختلف كلياً (`patient` وليس `role`).
2. Endpoints جديدة تحت `/patient/*` بدل `/admin/*`، بفحص "هل هذا المريض صاحب هذا السجل فعلاً؟" بدل فحص صلاحية دور.
3. نقطة التكامل المستقبلية مع EMR (Electronic Medical Record) موضّحة أصلاً كـ Future Initiative في `PLATFORM_KNOWLEDGE_BASE.md` — تُضاف كموديول `MedicalRecords` منفصل يرتبط بـ `Patient` فقط، بدون لمس بيانات المحتوى التسويقي الحالية إطلاقاً.

---

## 8. تكاملات ذكاء اصطناعي مستقبلية

البنية الحالية (`AiProviderAdapter` في `../architecture/01_ARCHITECTURE.md`) مصمَّمة لتوسّعات مثل:
- **مساعدة كتابة الأخبار:** اقتراح مسودة عربي/إنجليزي تلقائياً من نص خام يُدخله الأدمن — نفس الـ Adapter، موديول جديد `ai-content-assist` منفصل عن `ai-chat`.
- **تحليلات تنبؤية للعمليات:** (مثال: توقّع أوقات الذروة بالحجوزات) — يُبنى كموديول تحليلي منفصل يقرأ من نفس قاعدة البيانات دون التأثير على أي منطق حالي.
- **فرز أولي ذكي (AI Triage) لتليمديسن مستقبلي:** نقطة تكامل إضافية داخل موديول الحجز، مقيّدة بنفس مبدأ عدم التشخيص الطبي المباشر المطبّق على `ChatWidget` حالياً.

---

## 9. الاشتراكات والفوترة (مؤجّل عمداً — القرار المعتمد رقم 1)

نقطة الربط الجاهزة عند الحاجة الفعلية مستقبلاً:
1. موديول `billing/` جديد كلياً (`Plan`, `Subscription`, `Invoice`) — منفصل تماماً عن جداول المحتوى الحالية.
2. Adapter لبوابة دفع (مثال: Paymob لملاءمة السوق المصري، أو Stripe لو التوسّع دولي) بنفس فلسفة عدم القفل على مزوّد واحد.
3. **لا حاجة لأي تعديل بجداول Hospital/MedicalCenter الحالية** — البنية الحالية أصلاً لا تفترض نموذج عمل مجاني أو مدفوع، فهي محايدة تماماً تجاه القرار التجاري المستقبلي.

---

## 10. التوسّع لمنظومات متعددة (Multi-Tenant)

لو قررت INSAN مستقبلاً إدارة مجموعة مستشفيات أخرى منفصلة عن هذه المنظومة بالكامل (عميل/كيان مختلف):
1. إضافة جدول `Tenant`/`Organization` أعلى مستوى `Hospital` الحالي.
2. كل الجداول الأساسية أصلاً تحمل علاقات واضحة بـ `hospitalId` — تحويلها لعزل بيانات كامل بين المنظومات (Row-level isolation بـ `tenantId`) تعديل مضبوط ومحدود النطاق، وليس إعادة بناء.

---

**ملاحظة ختامية:** كل نقاط التوسّع أعلاه **لا تُبنى الآن** — هي فقط ضمان أن القرارات المعمارية الحالية (خصوصاً i18n بصيغة Json، `customFields`، العقد الموحّد للـ API، ونمط الأدوار القابل للتمديد) لن تحتاج إعادة هيكلة عند الحاجة الفعلية لأي منها مستقبلاً.
